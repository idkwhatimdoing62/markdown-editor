# ADR-0003：长文档采用分层基准和容量预算

- 状态：已接受
- 日期：2026-08-13

## 背景

应用允许读取不超过 10 MiB 的 Markdown，但“能读取”不能等同于“交互流畅”。一次文档更新会经过源码读取、Markdown 解析、浏览器 HTML 生成和 WebView DOM 装载；Windows 上还会产生多个 WebView2 子进程。只测 Rust 主进程或只测解析耗时，都会漏掉用户真正承担的启动时间和内存。

## 决策

建立 100 KiB、1 MiB、10 MiB 三档可重复语料，并在 `release` 构建下分别记录：

1. `parse_document` 的中位数和 P95；
2. 浏览器预览 HTML 的生成耗时与输出大小；
3. 主题一致导出 HTML 的生成耗时与输出大小；
4. 应用启动到 WebView 报告 DOM、字体和两帧布局完成的耗时；
5. 主进程及全部后代进程的峰值工作集、私有内存和 WebView 进程数。

脚本位于 `scripts/benchmark-long-docs.ps1`，原始 JSON 写入被 Git 忽略的 `artifacts/performance/`。默认命令用于采样：

```powershell
.\scripts\benchmark-long-docs.ps1
```

发布前或性能改动后使用预算检查：

```powershell
.\scripts\benchmark-long-docs.ps1 -EnforceBudgets
```

初始预算是同机回归护栏，不是产品体验目标：

| 规模 | 解析 P95 | 预览 HTML P95 | 导出 HTML P95 | WebView 就绪 | 进程树峰值工作集 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 100 KiB | 20 ms | 30 ms | 200 ms | 2 s | 900 MiB |
| 1 MiB | 150 ms | 200 ms | 500 ms | 3 s | 1.3 GiB |
| 10 MiB | 1 s | 6.5 s | 3.5 s | **5 s** | **2 GiB** |

内存数必须在相同操作系统、WebView2 版本和相近机器上比较。它包含浏览器进程树，不能与任务管理器里单独一行主进程的数字直接比较。

## 优化后基线与已发现问题

2026-08-13 在 Windows 11、Ryzen 5 7500F、32 GiB 内存机器上的首次完整基线约为：

| 规模 | 解析中位数 | 预览 HTML 中位数 | WebView 就绪 | 进程树峰值工作集 |
| --- | ---: | ---: | ---: | ---: |
| 100 KiB | 4.2 ms | 2.2 ms | 0.69 s | 677 MiB |
| 1 MiB | 30.5 ms | 32.5 ms | 0.94 s | 762 MiB |
| 10 MiB | 361 ms | 3.02 s | **4.13 s** | **1.27 GiB** |

2026-08-31 在同一台 Windows 性能机执行发布前复测（优化后工作树，WebView2 151.0.4129.107）：

| 规模 | 解析 P95 | 预览 HTML P95 | 导出 HTML P95 | WebView 就绪 | 进程树峰值工作集 | 预算结果 |
| --- | ---: | ---: | ---: | ---: | ---: | --- |
| 100 KiB | 4.57 ms | 1.82 ms | 53.89 ms | 0.71 s | 653 MiB | 通过 |
| 1 MiB | 27.19 ms | 16.50 ms | 55.84 ms | 0.74 s | 667 MiB | 通过 |
| 10 MiB | 283.07 ms | 164.80 ms | 99.56 ms | **1.70 s** | **987 MiB** | **通过** |

2026-08-31 WebView 生命周期优化采用同一脚本在改动前后各执行一次。该改动不以降低首次打开成本为目标，但仍需证明首次打开没有回退：

| 规模 | 改动前 WebView 就绪 | 改动后 WebView 就绪 | 改动前峰值工作集 | 改动后峰值工作集 |
| --- | ---: | ---: | ---: | ---: |
| 100 KiB | 0.82 s | 0.70 s | 681 MiB | 669 MiB |
| 1 MiB | 0.78 s | 0.72 s | 751 MiB | 679 MiB |
| 10 MiB | 1.79 s | 1.60 s | 1063 MiB | 1050 MiB |

首次打开差异处于 WebView2 进程启动和系统缓存波动范围内，因此只作为“无回退”证据，不宣称启动性能提升。生命周期改动的直接收益由引用释放测试守护：切换到写作模式或空工作区时，同时销毁 WebView、清空协议载荷与 Rust 侧预览缓存。当前 10 MiB 语料生成的预览载荷约为 17.5 MiB；改动前即使预览隐藏仍被两个 `Arc` 入口保留，改动后全部释放。分栏连续输入则复用上一版预览，在最后一次编辑 200 ms 后只重建一次；切换标签、主题、字号和目录时不复用旧上下文。

图片密集型预览使用 `scripts/benchmark-image-preview.ps1` 单独记录首屏前本地图片请求数。20 张 1600×1200 图片的初始行为是首屏前请求 20 张。给普通图片补浏览器原生 `loading="lazy"` 后仍请求 20 张，工作集也没有改善，因此该尝试已回退。最终方案把“超过 8 张图片”也作为虚拟预览触发条件，每个块最多包含 4 张图片，并按图片数量补足块的估算高度；相同语料的首屏前请求数降为 4 张，减少 80%，首屏时间保持约 0.62 秒。用户显式编写的 HTML 和主题 CSS 不需要改写图片属性。

Mermaid 预览使用 `scripts/benchmark-mermaid-preview.ps1` 单独记录首屏前运行库请求。内置 Mermaid 运行库为 3,565,102 字节；600 KiB 正文且图表位于文末时，原实现仍在首屏请求完整运行库，就绪约 0.74 秒、峰值工作集约 627 MiB。启动脚本改为检查当前 DOM，只有虚拟块中真正出现 Mermaid 代码块时才动态加载运行库；相同语料的首屏请求从 1 次降为 0 次，就绪约 0.60 秒、峰值工作集约 607 MiB。图表位于首屏的反向用例仍请求 1 次运行库并正常完成 WebView 就绪；渲染调用通过 Promise 队列串行化，避免多个虚拟块并发加载时重复初始化或重复渲染。

WebView 字体协议会记录四种字重的请求次数和总字节。100 KiB 中文语料使用原始 TTF 时，首屏会请求 JetBrains Mono Regular/Bold 与霞鹜文楷 Lite Regular/Medium 共 26.82 MiB；三次运行的中位就绪时间约 665 ms、峰值工作集约 669 MiB、峰值私有内存约 805 MiB。完整字形转换为 WOFF 后，请求降为 15.91 MiB，中位就绪约 596 ms、峰值工作集约 646 MiB、峰值私有内存约 782 MiB；发布二进制同时由约 90.8 MB 降为 79.4 MB。WOFF2 虽把请求进一步降至 10.58 MiB，但中位就绪回退到约 776 ms，因此未保留。`scripts/build-web-fonts.ps1` 从原始 TTF 可重复生成 WOFF；编辑区字体和 HTML/PDF 导出继续使用原始 TTF，不改变字形或字重。

使用 `scripts/benchmark-native-memory.ps1` 测试过 Windows/macOS 原生界面是否可以不常驻中文 Medium 字体。三次空窗口稳态工作集约 153.8 MiB、私有内存约 478.4 MiB，移除前后均在同一范围内，判定为无收益并回退；原生预览的粗体回退因此保持原样。

本次优化把代码语言标注从反复插入原字符串改为一次线性重建，避免长文档 HTML 生成的平方级复制；同时修复了基准二进制缺少 `theme` 和 `storage` 模块、导致脚本无法启动的问题。`-EnforceBudgets` 已成功完成三档检查。

基准建立和 P1 优化过程中修复了四项真实问题：

- 源码行锚点原先为每个块从文档开头重新计数，1 MiB HTML 生成约需 2 秒；改成一次建立行首索引后降到约 34 ms；
- 预览 HTML 原先在每个界面帧重复生成和哈希；现在按标签、文档版本、主题、字号和目录缓存，并按 `Arc` 身份判断是否变化；
- WebView2 的字符串导航通道不能可靠承载大 HTML；现在通过 `mdpreview` 内部协议响应文档，不再受 `load_html` 大小边界限制。
- 超过 512 KiB 的预览不再一次创建完整 DOM。Rust 按约 96 KiB 的顶层块边界生成虚拟块清单；WebView 首屏只加载一个块，滚动或目录定位时按源码范围加载附近块，并回收距离视口五屏以外的块。

虚拟块中的 Markdown 节点仍直接插入 `body`，因此 `body > h2` 等主题选择器保持有效。章节定位通过块内标题范围加载目标块；视口维护和目录跳转并发请求同一块时复用同一个进行中 Promise，目录跳转必须等标题进入 DOM 后再定位，保证首次点击生效。普通预览不再为每个离屏块设置 `content-visibility:auto` 和固定内在高度：这类近似高度会让首次远距离章节定位在真实布局展开后漂移；大文档容量仍由虚拟块加载与回收控制。源码滚动通过每块的源码起止位置映射；Mermaid 在块进入 DOM 后按需渲染。10 MiB 的 WebView 就绪时间和进程树峰值工作集已经达到 5 秒与 2 GiB 的 P1 门槛。

## 影响

- 性能回归有固定输入、分层数据和机器信息，不再依赖肉眼或单一任务管理器数字；
- WebView 基准会短暂打开应用窗口，并依赖本机 WebView2；它不适合作为每次单元测试的硬门禁；
- `-EnforceBudgets` 超限时返回失败，适合发布检查或固定性能机；
- 大文档的远端块使用估算高度，首次进入该块后以实际布局高度替换；源码定位会在加载后校正位置。

## 重新评估条件

- Markdown 文件上限改变；
- 解析器、主题兼容层、WebView 或导出引擎更换；
- 固定性能机连续两次越过预算；
- 需要把 10 MiB 的完整 HTML 生成或编辑输入延迟纳入更严格的实时体验承诺。
