# ADR-0004：先稳定 Core + Worker + Snapshot，再评估 UI 重写

- 状态：采用
- 日期：2026-09-14

## 背景

编辑器的源码、解析树、搜索结果和 egui 绘制目前处在同一个交互循环里。长文档输入时，任何一次解析或全文搜索都可能占住 UI 帧；异步结果如果没有版本标记，还会把旧内容绘制到新源码上。

## 决策

先保留当前 `eframe + egui + wgpu`，把数据边界拆成四层：

1. `document_core.rs` 持有源码、`ParsedDocument`、文档状态和两个 revision。源码变更只推进当前 revision；解析结果必须通过 revision 和源码校验才能安装。
2. `parse_worker.rs` 和 `search_worker.rs` 使用每标签一个待处理槽的 latest-wins mailbox。输入在交接点复制为 `Arc<str>`，结果携带标签、文档 revision（搜索另带 query generation）。
3. 预览与目录每帧最多取得一个不可变 `DocumentSnapshot`。解析尚未追上时，文档仍按上一版解析渲染，只有编辑器接管的段落切回源码编辑并显示“正在解析”；这一期间的块索引仍属于上一版解析，因此不参与点击命中。
4. 结果轮询只触发短暂 repaint；没有待处理任务时不建立永久定时刷新。

## 体验目标

- 连续输入不会把 Markdown 解析放在 UI 线程上，光标、滚动和标签切换保持可响应；
- 快速改文档或切换搜索词时，旧结果会被丢弃，不会出现内容倒退、错误高亮或跳回旧段落；
- 单个标签的长解析不会无限积压每次按键的源码副本，也不会吞掉其他标签的请求；
- 解析暂未完成时仍可继续编辑，完成后再恢复混合排版预览。

## 暂未纳入本 ADR 的工作

- 文件打开、HTML/PDF 导出和外部重载仍有同步路径，下一阶段再接入独立 worker；
- 当前 egui 预览仍会遍历已解析的全部块，视口块布局和高度缓存另行实现；
- `egui_kittest` 交互/截图测试、IPC 认证和跨平台真实窗口回归尚未作为本阶段完成条件。

## 重新评估条件

当 Core/Worker 的数据契约稳定且有真实长文档基准后，如果混合编辑、可访问性或复杂布局仍受 egui 限制，再用小型 Iced 原型验证 UI，而不是先承担整套迁移成本。
